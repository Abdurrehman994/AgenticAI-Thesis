# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Master's thesis code (Agentic AI for PLM). A pull-based agent finds missing attributes on Engineering Items in a
3DEXPERIENCE cloud tenant through the public `dseng` REST API, proposes values, and writes them back for human review.
The account has no Enterprise Integration Architect role, so there are no platform events: everything is polling REST.
Thesis phases: 1 access, 2 REST client, 3 agent logic (rule-based, done), 4 evaluation against ground truth.
SolidWorks is used only to read the sample models (`extract_cad.py`, COM, read-only) into the held-out dataset.

## Architecture

Three layers: `plm_client/` (REST client) → `agent/` (pipeline) → `scripts/` (CLIs).

**plm_client**
- `session.py`: every call gets the `SecurityContext` header and a `?tenant=` query parameter (the cloud tenant answers
  "tenant does not exist" without it); `ENO_CSRF_TOKEN` only on non-GET; one re-login on 401.
- `auth.py`: 3DPassport CAS login. The 3DSpace landing page returns 403 even when login succeeded, so the CSRF fetch is
  the real success check.
- `engineering.py` returns plain dicts. Search is `GET /dseng:EngItem/search?$searchStr=` (there is no POST search).
  Responses **omit empty attributes**, so a missing key means empty: use `agent.snapshot.field_value` / `part_number`.
  PATCH requires `cestamp`. Material is a `dsspec:Material` relationship and returns 403 for the current roles.
- `models/` is generated by datamodel-codegen from `docs/openapi/dseng-1.4.1.json` (a package because schema names
  contain dots). Nothing uses it yet.
- `recording.py`: vcrpy recorder that scrubs CAS tickets, `Set-Cookie` (CASTGC session cookies), `lt` and the CSRF token.
  Always record through `recorder()`, and check new cassettes for `TGT-`, `ST-` and `JSESSIONID`.

**agent pipeline** (`scripts/run_agent.py` wires it)
1. `Snapshot.load` searches the collab space once; children and where-used parents are fetched lazily and cached.
2. `find_gaps` is plain code (no AI) and skips `(item_id, field)` pairs that already have a pending proposal.
3. `Suggester.suggest(gap, snapshot) -> Proposal | None`. `RuleBasedSuggester` is the Phase 4 baseline;
   `LLMSuggester` (`agent/llm.py`) calls any OpenAI-compatible endpoint (`LLM_*` in `.env`; planned: Lehmus AI, the
   university's vLLM platform, reachable only from the university network or VPN; `LLM_MODEL` is the "public model
   id"). One request per gap, no tools, one retry on malformed JSON; it sets `last_call` (latency, tokens, error),
   which `run()` stores per gap. Every proposal carries `confidence`, `method` and `evidence`.
   `AgenticSuggester` (`agent/agentic.py`, `--suggester agent`) subclasses it: the model starts with the item, its
   parents' and children's titles, and calls tools over the snapshot (`SnapshotTools`: find_similar, get_siblings,
   get_item, get_parents, get_children, find_items, list_items). Tools are declared natively (`TOOL_SCHEMAS`, which
   also generates the prompt's tool list); `AgenticSuggester._ask` reads `tool_calls` from `LLMSuggester._message`,
   and an endpoint that rejects `tools` (HTTP 400) falls back to the plain JSON protocol `{"tool":..., "args":...}`
   in the prompt for up to `MAX_STEPS`, then answers in the same format. `VERSION` is part of
   the method label (`agent-v2:...`): bump it when the agent changes, so runs of each version stay separate.
   Its prompt reuses the fixed-context prompt's rules (`agent_prompt`); `last_call["steps"]` records the tool calls;
   in evidence mode only items it was shown (`SnapshotTools.seen`) count as sources.
   `run()` then drops every part number proposed for more than one item in the run (`ambiguous` in the run file):
   order independent, so a wrong early answer cannot block the right one.
4. `write_proposal` then `ProposalLog` (`runs/proposals.jsonl`): append-only events `proposed` / `approved` / `rejected`;
   status is derived by folding the events. `routed` (proposal sent to a route) keeps the status pending.
5. Review either with `review.py` or in the platform: `agent/review_route.py` builds one route (approval workflow,
   `plm_client/routes.py`, spec `docs/openapi/dsroute_v1.openapi.json`) with one Approve task per proposal; the task
   title starts with the proposal id. `sync` reads each task's `approvalStatus` / `comments` (`value: ...` = edited
   value) and calls the same `approve` / `reject`. Route search works with the current role (verified); creating a
   route has not been tried on the tenant yet, and `routeBasePurpose` / `AutoStopOnRejection` values beyond the
   spec's examples are unverified.
6. Continuous mode: `scripts/watch_agent.py` polls search, `agent/watch.py` `ChangeTracker` compares each item's
   `cestamp` with the last poll (state in `runs/watch-state.json`), and `run(..., only=changed_ids)` handles just those.
   `only` takes titles or ids and still loads the whole collab space, so the evidence equals a full run. An event
   handler (once the Enterprise Integration Architect role is granted) is meant to call the same `run(only=...)`.

Write-back contract: descriptions go into PLM as `[PROPOSED] value`; part numbers are identifiers, so they are never
prefixed, only logged, and written on approval. `approve` / `reject` detect conflicts by comparing the field's content,
not `cestamp` (items created together share a cestamp, and a second proposal on the same item changes it).

**Data and tests**
- `data/dataset.json` is ground truth: the true values plus the `blank` fields left empty in PLM. `data/seeded.json` maps
  title to item id in the tenant.
- `data/dataset_cad.json` is the held-out set, generated by `cad_to_dataset.py` (random blanks, fixed seed). A field
  missing from an entry has no CAD value: a gap with no ground truth. Do not tune the rules on it.
- `agent/offline.py` `DatasetTenant` builds an in-memory tenant from a dataset; the tests (`tenant` fixture) and
  `run_agent.py --dataset` run against it. Changing `dataset.json` changes the expected counts in `tests/test_agent.py`.
- SolidWorks keeps most descriptions in configuration-specific properties: `extract_cad.py` reads both tabs.
- `runs/run-*.json` records every gap of every run, including gaps with no proposal (Phase 4 input), and the
  `fields` the run checked; `evaluate.py` / `compare.py` grade only those (older runs: description, partNumber).
- Material: `dsspec:Material` returns 403, so `material` is an offline-only field (`--fields`, needs `--dataset`).
  `DatasetTenant` stores it as an item key; `cad_to_dataset.py` blanks it with its own random stream (seed + 1) so
  the description and part number blanks stay as they were. Material proposals are never written to PLM.

## Tenant behaviour that differs from the spec

Verified on the tenant; details in `docs/spec-notes.md`.
- BOM links and where-used (`locate`) need `source` = `PLM_SPACE_URL` and
  `relativePath` = `/resources/v1/modeler/dseng/dseng:EngItem/{id}`. The spec's `$3DSpace` examples are rejected.
- A batch `POST /dseng:EngItem` copies the previous item's part number onto items created without one: create one
  item per call.
- `GET .../dseng:EngInstance` returns children in no particular order: never rely on BOM position.
- Search and where-used are index based and lag a few minutes behind creates and new links.
- Clear a part number with `DELETE /dseng:EngItem/{id}/dseng:EnterpriseReference`.
- PATCH with `description: ""` clears a description (used by `reject`).
